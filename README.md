# PDCA Insights Reporter

A conversational assistant for the **manufacturing department only**. It answers plain-English questions about PDCA (Plan-Do-Check-Act) improvement cycles: status, overdue actions, "did the countermeasure work?", "have we seen this before?" and a weekly review brief.

> **All data in this repository is synthetic.** It was generated by `scripts/generate_data.py` (seed 42, as-of 2026-11-02) for a course project. No real company, plant or person is described.

- **Live app:** https://pdca-insights-reporter.vercel.app (no sign-in)

## What it does (MVP)

| Feature | Example question | How it answers |
|---|---|---|
| F1 Ask PDCA status and overdue | "Which cycles on Line 2 are stuck in Check?" | Read-only tools filter cycles and actions in code |
| F2 Did it work? | "Did the countermeasure on PDCA-017 work?" | Before/after KPI vs target computed in code (28-day windows, 7-day minimum) |
| F3 Seen before? | "Have we seen weld porosity before?" | BM25 search over lessons learned with a synonym list and a match threshold |
| F4 Weekly brief | "Write this week's PDCA brief for the plant head" | Aggregates from tools, then a cited summary |

## How it stays trustworthy

1. **The model never does the maths.** It picks from 9 fixed read-only tools (`lib/tools.js`); code returns every number.
2. **Grounding check.** Every number and ID in the answer must appear in the tool results, or the answer is replaced with the raw tool output (`grounding_failed`).
3. **Scope and safety gates.** Non-manufacturing, unsafe (machine settings, bypassing guards), people-ranking, prompt-injection and write requests are declined.
4. **Honest states.** `answer`, `not_in_data`, `insufficient_evidence`, `declined`, `grounding_failed`.
5. **Read-only.** No free-form SQL, no writes, no messages sent.

## Models

Free tiers only:
- Primary: Groq `openai/gpt-oss-120b` on the free tier (fast; about 8,000 tokens per minute, so roughly 1-2 questions a minute)
- First fallback: Groq `openai/gpt-oss-20b` (its own free daily quota)
- Second fallback: OpenRouter `google/gemma-4-31b-it:free` (free model with tool calling, used automatically if Groq fails or is rate-limited)
- A short rate-limit pause (up to 8 s) is retried once before falling back.
- The model that answered is shown on each reply and in the header badge.

## Run locally

```bash
node --version            # 20 or later
cp .env.example .env      # add your keys; never commit .env
npm test                  # deterministic tool checks, no API calls
npx vercel dev            # serves public/ and api/ on http://localhost:3000
```

Regenerate the synthetic data and eval sets:

```bash
python3 scripts/generate_data.py
node scripts/build_evals.js
```

## Deploy (Vercel free tier)

1. Import the GitHub repo in Vercel (no framework, no build command).
2. Add `GROQ_API_KEY` and `OPENROUTER_API_KEY` as **environment variables in Vercel**. The live app is an inline deploy whose functions load `lib/` and `data/` from this repo at the commit in `SOURCE_REF`. Keys never go in the repo, code or docs.
3. Deploy. `/api/health` shows which models are configured (never the keys).

## Evals

- `evals/dev.json` (61 items) and `evals/holdout.json` (30 items). Expected values come from the tools, not hand-typed.
- Types: answer (must include facts, expected tools), not_in_data, decline, injection.
- Run against a deployment with `EVALS_ENABLED=true`: `/api/evals?set=dev&from=0&n=16`, then turn the flag off.
- Targets (from the PRD): safety gates 100%, answer accuracy 95%+, tool selection 90%+, recall@3 90%+, p95 latency under 6 s.

### Live results (4 Nov 2026, free tier)

| Set | Safety (decline + injection) | Answer accuracy | Notes |
|---|---|---|---|
| Dev, 61 items | 14/14 (100%) | 44/47 (94%); 44/45 of questions that reached a model (98%) | First pass on gpt-oss-120b; 4 failure causes fixed, failed items re-run on gpt-oss-20b |
| Held-out, 30 items | 10/10 (100%) | 16/20 (80%); 16/18 answered (89%) | Ran on gpt-oss-20b fallback because the 120b free daily quota was used up |

- Every failure was either a free-tier rate limit (no answer, safe error shown) or the grounding check blocking an answer with an untraced number or ID (raw tool data shown instead). No ungrounded number reached the user.
- Tool selection: correct tool on every answered question.
- Latency: median about 2.4 s, p95 7.1 s (target under 6 s, not yet met).
- Tokens: about 4,074 input and 590 output per question (measured). Raw rows: `evals/results/`.
- To do: re-run the held-out set on gpt-oss-120b when its daily quota resets.

## Synthetic dataset

`data/pdca.json`: 68 cycles (38 open, 30 closed), 140 actions, 30 lessons learned. `data/kpi_readings.json`: 1,470 daily readings (OEE, scrap %, downtime, FPY) for Lines 1-4, shifts A and B, May to Nov 2026.

It matches the discovery story: 38 open cycles, 11 stuck in Check for more than 14 days, 27 of 140 actions overdue, 9 cycles closed without KPI verification, 3 recurring defects. Planted data gaps for testing: missing owners (PDCA-005, PDCA-020, ACT-002 to 006), missing baseline or target (PDCA-010, PDCA-028), a duplicate (PDCA-031 of PDCA-013), missing due dates, and a 10-day KPI gap on Line 3 shift B. Showcase: PDCA-017 (Line 2 scrap 4.2% to 2.6%, target 2.5%).
